# 大模型如何判断何时调用 MCP

在支持 MCP（Model Context Protocol）的 Agent 系统中，大模型可以直接回答，也可以调用 MCP Server 提供的工具。模型并不是先理解 MCP 的网络协议再作决定，而是根据当前上下文中提供的工具描述，预测下一步应该生成普通文本还是结构化的工具调用。

## 一、MCP 在调用链中的位置

一个典型流程如下：

```text
用户
  -> Agent / MCP Client
  -> 大语言模型
  -> 选择直接回答或请求调用工具
  -> MCP Client 执行 MCP 工具
  -> 将工具结果返回给模型
  -> 模型生成最终回答
```

MCP 负责标准化客户端与外部工具、资源和提示模板之间的连接。真正执行工具的是 MCP Client 或宿主应用，不是大模型本身。

## 二、模型能看到什么

宿主应用会把可用工具及其说明放入模型上下文。每个工具通常包含：

- 工具名称
- 功能描述
- 参数定义
- 参数类型与必填项
- 可选的使用约束

例如：

```json
{
  "name": "get_weather",
  "description": "查询指定城市的实时天气",
  "parameters": {
    "city": {
      "type": "string",
      "description": "城市名称"
    }
  }
}
```

当用户问“上海现在天气怎么样”时，模型发现问题需要实时信息，而 `get_weather` 的描述与任务高度匹配，因此更可能输出工具调用。

## 三、模型如何做选择

从模型视角看，直接回答和工具调用都是下一步输出的候选形式。

```text
候选 A：生成普通文本答案
候选 B：生成 tool_call(get_weather, {"city": "上海"})
```

模型根据系统提示、用户意图、工具描述、对话历史和训练中学到的行为模式，为不同候选分配概率，然后选择更合适的动作。

模型倾向调用工具的典型情况包括：

1. **需要实时信息**：天气、股价、新闻和当前系统状态。
2. **需要私有数据**：企业文档、数据库记录、用户邮件。
3. **需要执行操作**：发送消息、创建工单、修改文件。
4. **需要精确计算**：复杂数学、代码执行、数据分析。
5. **系统明确要求**：规定某类问题必须通过指定工具处理。

模型倾向直接回答的情况包括：

- 普通知识解释
- 不依赖实时信息的概念问题
- 仅需改写、总结或翻译当前上下文
- 工具无法帮助完成任务

## 四、为什么有时会选错

工具选择不是硬编码判断，而是概率决策，因此可能出现错误。

### 应调用却直接回答

原因可能是工具描述不清晰、模型认为自身知识足够，或系统提示没有强调实时性与准确性要求。

### 不需要却调用工具

原因可能是工具描述过于宽泛，或者系统提示过度鼓励调用工具。

### 选择了错误工具

当多个工具名称和描述相似时，模型可能无法区分各自边界。

### 参数填写错误

工具参数过多、命名模糊或缺少示例时，模型更容易遗漏或误填参数。

## 五、如何提高工具选择准确率

### 1. 编写清晰的工具描述

工具描述应说明它做什么、何时使用，以及何时不应使用。

```text
查询实时天气。仅在用户询问当前或未来天气时使用；
不要用于解释气候、季节等一般知识。
```

### 2. 让工具职责单一

一个工具只处理一种明确任务，比一个接收大量可选参数的万能工具更容易被正确选择。

### 3. 使用明确的参数定义

参数名称、类型、枚举值和描述越清晰，模型越容易生成合法调用。

### 4. 在系统提示中制定规则

例如：

```text
涉及实时数据时必须调用工具，不得凭记忆回答。
执行写操作前必须先获得用户确认。
```

### 5. 在应用层增加控制

高风险操作不能完全依赖模型判断。宿主应用应增加权限检查、参数校验、用户确认、超时、重试和审计日志。

### 6. 建立工具调用评测集

为“应调用”“不应调用”“应该调用哪个工具”等场景建立测试用例，持续评估模型的选择准确率。

## 六、MCP 与 Function Calling 的关系

Function Calling 是模型输出结构化工具调用的一种能力；MCP 是宿主应用发现、连接和调用外部能力的一种标准协议。

可以简单理解为：

```text
Function Calling：模型如何表达“我要调用这个工具”
MCP：应用如何发现工具、执行工具并返回结果
```

两者经常配合使用，但职责不同。

## 七、一个完整示例

用户提出问题：

```text
帮我查看今天未读的工作邮件，并总结最紧急的三封。
```

模型的决策过程可以概括为：

1. 当前上下文中没有用户的实时邮件数据。
2. 可用工具中存在邮件搜索工具。
3. 该任务只需读取数据，不需要发送或删除邮件。
4. 模型生成邮件搜索工具调用。
5. MCP Client 执行调用并返回邮件列表。
6. 模型根据结果判断紧急程度并生成总结。

如果用户只是问“如何判断一封邮件是否紧急”，模型通常可以直接回答，因为该问题不依赖用户的真实邮箱数据。

## 总结

大模型知道何时调用 MCP 工具，主要依靠：

```text
用户意图
+ 系统提示中的规则
+ 工具名称、描述和参数
+ 对话上下文
+ 工具调用训练形成的行为模式
```

模型负责提出调用请求，MCP Client 负责实际执行。要构建可靠的 Agent，不能只依赖模型的概率判断，还需要清晰的工具设计和应用层安全控制。
