# 测试方法

```

│                      测试方法分类                               │
├─────────────────────────────────────────────────────────────────┤
```

## 二、黑盒测试

### 2.1 定义

黑盒测试也称功能测试，将软件看作一个黑盒子，不考虑内部结构和实现，只根据需求规格说明书检查程序的功能是否正确。

### 2.2 特点

| 特点 | 说明 |
|------|------|
| **视角** | 从用户角度测试 |
| **依据** | 需求规格说明书 |
| **关注点** | 输入和输出的对应关系 |
| **不关注** | 内部实现细节 |

### 2.3 适用场景

- 功能测试
- 系统测试
- 验收测试
- 非技术人员执行测试

### 2.4 黑盒测试方法

| 方法 | 说明 |
|------|------|
| **等价类划分** | 将输入划分为若干等价类，从每个类中选取代表性数据 |
| **边界值分析** | 在边界值附近选取测试数据 |
| **因果图法** | 分析输入条件之间的组合关系 |
| **判定表法** | 列出所有可能的条件组合 |
| **场景法** | 基于业务场景设计测试用例 |
| **错误推测法** | 根据经验推测可能出错的地方 |

## 三、白盒测试

### 3.1 定义

白盒测试也称结构测试，根据软件内部结构和逻辑进行测试，检查内部操作是否按规定执行。

### 3.2 特点

| 特点 | 说明 |
|------|------|
| **视角** | 从开发者角度测试 |
| **依据** | 详细设计文档、源代码 |
| **关注点** | 内部逻辑、代码路径 |
| **需要** | 了解代码结构 |

### 3.3 适用场景

- 单元测试
- 集成测试
- 代码审查
- 开发人员执行测试

### 3.4 白盒测试方法

| 方法 | 说明 |
|------|------|
| **语句覆盖** | 每条语句至少执行一次 |
| **分支覆盖** | 每个判断的真假分支都执行 |
| **条件覆盖** | 每个条件的真假都取到 |
| **分支-条件覆盖** | 同时满足分支覆盖和条件覆盖 |
| **条件组合覆盖** | 所有条件的各种组合都出现 |
| **路径覆盖** | 覆盖所有可能的执行路径 |

### 3.5 覆盖率示例

```javascript
function example(a, b) {
  if (a > 0 && b > 0) {    // 条件1: a > 0, 条件2: b > 0
    return a + b;          // 语句1
  } else {
    return 0;              // 语句2
  }
}
```

**测试用例设计**：

| 测试用例 | a | b | 语句覆盖 | 分支覆盖 | 条件覆盖 |
|----------|---|---|----------|----------|----------|
| TC1 | 1 | 1 | 语句1 ✓ | 真分支 ✓ | a>0 ✓, b>0 ✓ |
| TC2 | -1 | -1 | 语句2 ✓ | 假分支 ✓ | a>0 ✗, b>0 ✗ |
| TC3 | 1 | -1 | 语句2 ✓ | 假分支 ✓ | a>0 ✓, b>0 ✗ |
| TC4 | -1 | 1 | 语句2 ✓ | 假分支 ✓ | a>0 ✗, b>0 ✓ |

## 四、灰盒测试

### 4.1 定义

灰盒测试介于黑盒测试和白盒测试之间，既关注功能需求，又关注部分内部实现。

### 4.2 特点

- 了解部分内部结构
- 结合黑盒和白盒方法
- 关注接口和数据交互

### 4.3 适用场景

- 集成测试
- API 测试
- 数据库测试

---

## 五、静态测试 vs 动态测试

### 5.1 静态测试

不运行程序，通过分析代码或文档发现缺陷。

| 方法 | 说明 |
|------|------|
| **代码审查** | 人工检查代码 |
| **代码走查** | 团队一起检查代码 |
| **静态分析** | 使用工具自动检查代码 |

**常见静态分析工具**：

| 语言 | 工具 |
|------|------|
| JavaScript | ESLint, JSHint |
| TypeScript | TSLint, ESLint |
| Python | Pylint, Flake8 |
| Java | Checkstyle, SonarQube |

### 5.2 动态测试

运行程序，通过观察运行结果发现缺陷。

- 单元测试
- 集成测试
- 系统测试
- 验收测试

---

## 六、手工测试 vs 自动化测试

### 6.1 手工测试

由测试人员手动执行测试用例。

**优点**：
- 灵活性高
- 可以发现意外问题
- 不需要编程技能

**缺点**：
- 效率低
- 重复性差
- 容易出错

### 6.2 自动化测试

使用工具或脚本自动执行测试。

**优点**：
- 效率高
- 可重复执行
- 结果一致

**缺点**：
- 需要编程技能
- 前期投入大
- 维护成本高

### 6.3 自动化测试工具

| 类型 | 工具 |
|------|------|
| **单元测试** | Jest, Mocha, Pytest, JUnit |
| **UI 自动化** | Selenium, Cypress, Playwright |
| **API 测试** | Postman, RestAssured, JMeter |
| **性能测试** | JMeter, Locust, Gatling |

## 总结

| 测试方法 | 视角 | 适用阶段 | 关注点 |
|----------|------|----------|--------|
| **黑盒测试** | 用户 | 系统测试、验收测试 | 功能正确性 |
| **白盒测试** | 开发者 | 单元测试 | 代码逻辑 |
| **灰盒测试** | 混合 | 集成测试 | 接口和数据 |
| **静态测试** | - | 任何阶段 | 代码质量 |
| **动态测试** | - | 测试执行 | 运行结果 |
