# D2C 知识检索 Agent 设计

知识检索 Agent 是 D2C 流水线的第三个阶段。它根据组件 DSL，从知识库中检索当前项目使用的组件库文档、代码规范和示例，并将这些资料提供给代码生成 Agent。

```text
组件 DSL -> 知识检索 Agent -> DSL + 项目知识
```

## 一、为什么模型自身知识不够

大模型可能了解 React、Vue 和常见 UI 组件，但它通常不知道当前项目的真实约束，例如：

- 项目使用哪个组件库及具体版本
- 内部组件有哪些属性和插槽
- 组件应该从哪个路径导入
- 团队规定使用哪些样式方案
- 表单、弹窗和请求如何封装
- 项目中已有的组件示例

如果仅依赖模型参数知识，生成代码可能语法正确，却无法在真实项目中运行。

## 二、知识检索 Agent 的设计目标

1. 从 DSL 中识别需要的组件与能力
2. 为每类组件构造检索查询
3. 从向量数据库中召回相关资料
4. 对资料进行过滤、排序和去重
5. 将准确、有限的上下文交给代码生成阶段

例如，DSL 中出现表单和日期选择需求时，检索 Agent 可以提供项目中 `Form`、`DatePicker` 的 API 文档与示例。

## 三、为什么需要独立检索阶段

如果让代码生成 Agent 同时搜索资料和生成代码，会出现以下问题：

- 检索过程难以观察和调试
- 无法判断错误来自资料召回还是代码生成
- 同一组件文档会被重复检索
- 很难单独评估检索准确率
- 生成模型可能忽略检索动作，凭记忆编写代码

独立检索阶段可以缓存结果，并明确记录每个组件使用了哪些知识来源。

## 四、为什么使用 RAG

组件库和项目规范会不断变化，不适合全部写入模型参数。RAG 可以在不重新训练模型的情况下更新知识。

```text
组件文档
  -> 分块与向量化
  -> ChromaDB
  -> 根据 DSL 召回相关资料
  -> 提供给代码生成 Agent
```

与微调相比，RAG 更适合保存需要频繁更新、需要引用来源的项目知识。

## 五、检索内容应该包含什么

| 知识类型 | 示例 |
| --- | --- |
| 组件 API | 属性、事件、插槽、导入路径 |
| 使用示例 | 表单、列表、弹窗的真实代码 |
| 项目规范 | 命名规则、目录结构、样式约束 |
| 业务组件 | 内部组件用途与调用方式 |
| 错误经验 | 常见错误与修复方法 |

检索结果应尽量简洁、准确。召回过多无关文档会占用上下文，并干扰代码生成。

## 六、失败风险与验证方式

常见失败包括：

- DSL 组件名称过于模糊，无法形成准确查询
- 召回了旧版本文档
- 相似度高但实际无关
- 重要组件文档没有被召回
- 多份资料互相冲突

可以通过 Recall@K、人工标注查询集、版本元数据过滤、重排序和来源引用检查评估检索质量。

## 总结

知识检索 Agent 负责把通用大模型连接到当前项目的真实技术环境。它让代码生成阶段不再只依赖模型记忆，而是基于最新组件文档、项目规范和真实示例生成代码。
