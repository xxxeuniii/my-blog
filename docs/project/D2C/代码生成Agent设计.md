# D2C 代码生成 Agent 设计

代码生成 Agent 是 D2C 流水线的第四个阶段。它接收组件 DSL 和知识检索结果，将结构化设计信息组织为可运行、可维护的前端代码。

```text
组件 DSL + 项目知识 -> 代码生成 Agent -> React / Vue / HTML
```

## 一、为什么代码生成适合使用大模型

前面的数据清洗和结构转换存在明确规则，而代码生成需要同时处理更多开放问题：

- 根据组件语义选择合适的标签和组件
- 组织页面、组件和状态代码
- 根据上下文生成变量名和事件处理函数
- 应用组件库 API 和项目规范
- 在视觉还原与代码可维护性之间取得平衡

这些任务很难通过固定模板覆盖所有情况，却适合大模型根据上下文进行组合和生成。

## 二、为什么不能直接从 Figma 生成代码

如果代码生成 Agent直接接收原始 Figma JSON，它还需要完成清洗、结构理解、组件识别和资料查询，任务范围过大。

经过前置 Agent 后，输入已经变成：

- 精简、稳定的组件 DSL
- 明确的页面层级
- 标准化的布局和样式
- 项目组件库文档与规范

代码生成 Agent 可以集中处理“如何写出高质量代码”，而不是重复解决数据解析问题。

## 三、代码生成 Agent 的设计目标

1. 严格按照 DSL 还原页面结构
2. 优先使用检索到的项目组件
3. 生成目标框架要求的完整代码
4. 遵守导入、命名、样式和目录规范
5. 尽量减少无意义的绝对定位和重复代码
6. 输出可供测试验证 Agent 检查的结果

## 四、为什么需要约束模型输出

大模型具有创造性，但代码生成阶段需要可控。提示词和输出协议应明确规定：

- 目标框架和语言
- 可使用的依赖
- 组件导入路径
- 输出文件结构
- 是否允许添加模拟数据
- 禁止编造不存在的组件 API
- 必须遵循 DSL 的节点层级

必要时可以要求模型输出结构化结果，例如文件名、代码内容和依赖列表。

## 五、为什么单独设计代码生成阶段

独立代码生成 Agent 便于：

- 替换或对比不同大模型
- 针对 React、Vue 使用不同提示词
- 单独记录 Token、延迟和生成质量
- 在失败时重新生成，而不重复执行前面步骤
- 对生成结果进行专门测试和修复

## 六、失败风险与验证方式

常见失败包括：

- 编造不存在的组件或属性
- 遗漏导入和类型定义
- 页面结构与 DSL 不一致
- 样式视觉还原不足
- 生成重复、难维护的代码
- 为了视觉效果过度使用绝对定位

可以通过编译检查、Lint、组件 API 校验、视觉对比和人工代码审查评估生成质量。

## 总结

代码生成 Agent 是将结构化设计真正落地为前端代码的阶段。它利用大模型处理开放的代码组织问题，同时依赖前置 Agent 提供清晰结构和项目知识，从而减少幻觉并提高代码可用性。
