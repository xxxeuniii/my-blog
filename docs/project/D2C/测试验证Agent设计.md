# D2C 测试验证 Agent 设计

测试验证 Agent 是 D2C 流水线的最后一个阶段。它负责检查代码生成 Agent 的输出，发现语法、依赖、安全、组件 API 和视觉还原问题，并在条件允许时自动修复。

```text
生成代码 -> 测试验证 Agent -> 检查报告 / 修复后的代码
```

## 一、为什么生成代码后还需要验证

大模型生成的是概率结果。即使输入结构和知识资料都正确，也可能出现：

- 标签、括号或字符串没有闭合
- 忘记导入组件或依赖
- 使用不存在的组件属性
- TypeScript 类型错误
- 列表缺少 `key`
- 生成存在 XSS 风险的代码
- 页面能够编译，但视觉结构与设计稿不一致

如果没有验证阶段，错误会直接交给开发者，D2C 只能完成“生成”，无法保证“可用”。

## 二、测试验证 Agent 的设计目标

1. 检查代码是否能够解析和编译
2. 验证导入、组件 API 和依赖是否正确
3. 检查常见安全与代码质量问题
4. 比较生成结构与 DSL 是否一致
5. 输出清晰的错误报告
6. 对低风险问题进行自动修复

## 三、为什么需要规则检查与大模型审查结合

确定性问题适合使用编译器、AST 和静态规则检查：

- 标签和括号匹配
- 未定义变量
- 缺失导入
- TypeScript 类型错误
- 危险 API 使用

开放性问题更适合大模型辅助判断：

- 组件划分是否合理
- 代码是否可维护
- 是否正确理解业务语义
- 修复方案如何最小化影响

使用静态检查作为第一道防线，再让大模型处理复杂问题，比完全依赖模型自检更可靠。

## 四、为什么不能让代码生成 Agent 自己保证正确

让同一个模型在一次生成中同时写代码并自我验证，容易忽略自身错误。独立验证阶段可以使用不同上下文、不同规则，甚至不同模型进行检查。

职责拆分还带来以下好处：

- 可以重复验证而不重新生成
- 可以记录错误类型和发生频率
- 可以衡量不同代码生成模型的质量
- 可以将失败反馈回具体阶段
- 可以逐步建立自动修复闭环

## 五、建议的验证层次

### 1. 语法与 AST 检查

确认代码可以被解析，标签、括号和语法结构完整。

### 2. 编译与类型检查

运行目标项目的构建、TypeScript 和 Lint 命令。

### 3. 组件与依赖检查

确认组件真实存在、导入路径正确、属性符合检索到的文档。

### 4. 安全检查

检查 XSS、危险 HTML 注入、硬编码密钥和不安全依赖使用。

### 5. 视觉验证

运行生成页面并与设计稿截图比较，检查布局、颜色、间距和字体差异。

## 六、自动修复的边界

适合自动修复的问题包括：

- 补全缺失导入
- 修复简单语法错误
- 添加列表 `key`
- 替换明确错误的组件属性

涉及业务逻辑、权限、安全或大规模结构变化时，应输出报告并交给开发者确认，避免自动修复引入更严重问题。

## 七、如何评估验证 Agent

可以关注以下指标：

- 首次生成代码的编译通过率
- 验证后代码的编译通过率
- 错误检出率与误报率
- 自动修复成功率
- 视觉相似度
- 人工接管和修改次数

## 总结

测试验证 Agent 为 D2C 建立了生成后的质量闭环。它将“看起来像代码”的模型输出，逐步验证为能够编译、符合规范并尽量还原设计稿的可用代码。
