D2C 数据清洗 Agent 设计 ​

在 D2C 项目中，第一个处理阶段是数据清洗 Agent。它负责接收从 Figma 导出的原始节点数据，删除与前端界面渲染无关的内容，并将复杂、松散的设计数据整理为后续 Agent 可以稳定处理的输入。

数据清洗并不是一个可有可无的预处理步骤。Figma 原始数据是为了支持设计工具自身的编辑、协作、版本管理和渲染能力而设计的，并不是专门为生成前端代码准备的。

一、Figma 原始数据有什么问题 ​

从 Figma API 或设计文件导出的原始 JSON，通常包含完整的文档树和大量节点属性。

一个简单页面在视觉上可能只有标题、按钮、图片和卡片，但导出的数据中可能存在成百上千个节点。每个节点还会携带大量属性，例如：

  • 节点 ID、组件 ID、实例 ID
  • 文件版本号、更新时间、编辑信息
  • 插件数据和协作相关信息
  • 约束、导出配置和设计工具内部状态
  • 不可见图层、锁定图层和辅助图层
  • 默认值、空数组和重复继承的样式
  • 前端代码生成暂时无法使用的高级效果

这些数据对于 Figma 正常运行很重要，但大部分不会影响最终网页的视觉结果。

例如，下面是一段简化后的原始节点数据：

json
{
  "id": "42:108",
  "name": "Primary Button",
  "type": "FRAME",
  "visible": true,
  "locked": false,
  "version": "384927104",
  "pluginData": {},
  "exportSettings": [],
  "absoluteBoundingBox": {
    "x": 120,
    "y": 240,
    "width": 160,
    "height": 48
  },
  "layoutMode": "HORIZONTAL",
  "itemSpacing": 8,
  "fills": [
    {
      "type": "SOLID",
      "color": { "r": 0.12, "g": 0.35, "b": 0.95, "a": 1 }
    }
  ],
  "children": []
}

对于生成前端代码来说，真正关键的内容主要是节点类型、尺寸、布局、颜色和子节点关系。版本号、插件数据和空导出配置等字段没有必要进入后续流程。

二、为什么不能直接把原始数据交给大模型 ​

将完整 Figma JSON 直接发送给大模型，看起来实现简单，但会产生一系列问题。

1. 消耗大量 Token ​

Figma 原始节点数据体积很大。大量无关字段会占用上下文窗口，提高请求成本，并降低处理速度。

模型真正需要理解的是界面结构和视觉属性。如果上下文中充满版本号、内部 ID 和空字段，重要信息反而更难被关注。

2. 增加模型判断难度 ​

原始数据中同时包含设计语义、工具内部状态和协作元数据。模型需要先判断哪些字段有用，再进行结构理解和代码生成。

这会把多个职责混在一次调用中，使输出更加不稳定。

3. 容易生成无关代码 ​

如果输入没有明确过滤，模型可能错误解释某些字段，将不需要的绝对坐标、隐藏节点或设计工具属性写入代码。

4. 降低后续 Agent 的稳定性 ​

后续结构转换、知识检索和代码生成 Agent 都依赖统一输入。未经清洗的原始数据字段复杂、变化频繁，会增加每个阶段的处理难度。

三、数据清洗 Agent 的设计目标 ​

数据清洗 Agent 的目标不是简单压缩 JSON，而是生成一个面向前端渲染的中间数据层。

它需要做到：

  1. 删除与最终界面无关的字段
  2. 保留能够决定界面结构和视觉效果的信息
  3. 过滤不需要生成代码的节点
  4. 统一颜色、尺寸和布局等数据格式
  5. 为后续结构转换提供稳定的数据协议

可以将整个过程理解为：

text
Figma 原始节点数据
  -> 删除工具内部元数据
  -> 过滤无效与不可见节点
  -> 提取布局和视觉属性
  -> 统一字段格式
  -> 面向前端渲染的干净数据

四、哪些数据应该删除 ​

具体清理规则需要根据项目需求调整，但以下数据通常可以删除或缩减。

1. 版本与协作元数据 ​

例如文件版本号、编辑时间、编辑者信息和协作状态。这些字段用于设计文件管理，不会影响页面渲染。

2. 工具内部标识 ​

大部分节点 ID、实例内部引用和插件数据不需要传递给代码生成阶段。

但如果节点 ID 需要用于调试、组件映射或增量更新，则应保留一个简化后的引用字段，而不是全部删除。

3. 空字段与默认值 ​

空数组、空对象和没有改变行为的默认值会显著增加 JSON 体积，可以在清洗阶段统一删除。

4. 不可见节点 ​

visible: false 的隐藏图层通常不需要生成代码。如果项目需要支持响应式状态或交互切换，则应结合业务规则决定是否保留。

5. 与代码生成无关的导出配置 ​

某些图片导出设置、设计工具操作状态和辅助信息不会参与网页渲染，可以移除。

五、哪些数据必须保留 ​

清洗不能只追求数据量更小。删除了关键字段，会导致最终代码无法还原设计稿。

通常需要保留：

数据类型作用
节点类型判断节点应转换为容器、文本、图片还是组件
节点名称辅助识别业务语义和组件用途
父子关系还原页面层级和组件嵌套
尺寸与位置决定元素大小及布局关系
自动布局属性转换为 Flexbox、间距和对齐方式
颜色、透明度与边框生成视觉样式
字体、字号和行高生成文本样式
圆角、阴影和效果还原组件外观
图片引用生成图片资源和背景

清洗规则的核心原则是：删除设计工具运行所需但页面渲染不需要的数据，保留决定最终视觉结果和组件结构的数据。

六、清洗前后的数据变化 ​

清洗后的节点可以整理为更适合后续处理的形式：

json
{
  "name": "Primary Button",
  "type": "FRAME",
  "layout": {
    "direction": "row",
    "gap": 8,
    "width": 160,
    "height": 48
  },
  "style": {
    "backgroundColor": "#1f59f2"
  },
  "children": []
}

与原始数据相比，这份数据：

  • 字段数量更少
  • 字段含义更接近前端概念
  • 不包含版本号等无关信息
  • 更容易转换为 DSL
  • 更适合被大模型理解

七、为什么清洗阶段优先使用规则 ​

D2C 的数据清洗阶段采用确定性的 Python 规则，而不是让大模型直接完成清洗。

主要原因包括：

  • 相同输入可以得到相同输出
  • 字段删除和格式转换规则容易测试
  • 不需要消耗大模型 Token
  • 处理速度更快
  • 不会因模型幻觉误删关键字段
  • 出现问题时容易定位和修复

大模型更适合处理业务语义理解和代码生成等开放任务。对于字段过滤、颜色转换和节点遍历等确定性任务，普通程序通常更可靠。

虽然项目中称其为数据清洗 Agent，但它的核心并不一定是调用大模型。这里的 Agent 更强调它在流水线中承担独立职责，并拥有明确输入、输出和处理规则。

八、数据清洗如何帮助后续 Agent ​

帮助结构转换 Agent ​

清洗后的字段已经接近前端布局概念，结构转换 Agent 可以更容易将节点映射为组件 DSL。

帮助知识检索 Agent ​

清晰的组件类型和语义名称能够形成更准确的检索关键词，减少无关文档召回。

帮助代码生成 Agent ​

更短、更稳定的输入可以减少 Token 消耗，让模型重点关注组件结构、样式和业务语义。

帮助测试验证 Agent ​

统一的数据结构便于比较设计稿要求与生成代码，定位布局或样式丢失问题。

九、如何判断清洗规则是否合理 ​

可以从以下几个方面评估：

  1. 清洗后数据体积减少了多少
  2. 关键节点和视觉属性是否完整保留
  3. 相同设计稿是否始终得到相同结果
  4. 后续 DSL 转换是否还需要读取原始字段
  5. 生成页面与设计稿的视觉差异是否扩大
  6. 是否能追踪清洗过程中被删除的字段

为了避免误删，实际项目可以保留清洗日志，并使用小型设计稿建立回归测试。

总结 ​

Figma 原始节点数据服务于完整的设计工具，包含大量与前端界面渲染无关的冗余信息，例如版本号、内部 ID、插件数据、空字段和不可见节点。

数据清洗 Agent 位于 D2C 流水线的第一步，是为了把这种面向设计工具的数据，转换为面向前端代码生成的数据：

text
复杂的 Figma 原始数据
-> 可控、稳定、精简的渲染数据
-> 组件 DSL
-> 前端代码

只有先建立可靠的数据清洗边界，后续 Agent 才能在更少噪声、更低成本和更稳定的输入上完成结构理解与代码生成。
